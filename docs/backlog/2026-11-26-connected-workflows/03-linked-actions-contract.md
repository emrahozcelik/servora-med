Stage actions explicitly: IMMEDIATE existing allowed command (sale from eligible visit); PROPOSE manager-reviewed work; CREATE approved downstream job; DEFERRED module-owned action. No action chains triggered merely by editing a note. Staff can propose other assignees only if approved policy permits; manager chooses valid active staff. No generic conversion endpoint accepting arbitrary source/target. Use server-produced contextual available actions with stable typed codes, disabled reason/next step where appropriate, and command-specific handlers/validators. Recheck authorization, source version, customer/assignee eligibility, state and feature/module at write boundary. UI copies customer/contact/product context only from authorized server snapshot; editable proposed quantities/details; do not leak linked IDs across owner scope. No automatic START or new geolocation requirement, preserve existing job approval. Same customer by default; explicit change only if existing approved policy permits (otherwise reject). Preserve independent orders.

## 2. Relationships
Existing source_job_card_id = follow-up lineage; sale_source_visit_id = commercial origin; delivery_source_sale_id = fulfillment provenance. Never overload these to mean arbitrary related work or count all relations as follow-up. Reuse typed lineage where semantics fit; new named relation/proposal table only when a concrete action needs it. Model source, target, relation kind, same-org refs, actor/time and immutable provenance. Prevent self-link, invalid type pairs, unauthorized cycles (bounded traversal and indexes); no arbitrary graph traversal on hot paths. For distinct repeatable actions use explicit intent identity, not title matching; define one active target per exclusive purpose where required. No universal dedup by customer; multiple legitimate visits allowed. Cancellation/invalidation do not cascade; retain history, display related status and manager exception queue. Existing SALE-002 pair owner/state reservation and expectedSaleVersion unaffected.

## 3. SALE-003: late delivery and replacement
Current 071 lifetime unique constraint and Q4 limitation intentionally prevent replacement. Proposed replacement:
- Manager/Admin only, source SALE is COMPLETED and not invalidated, customer/assignee eligible. New dedicated action on approved sale when delivery absent or prior attempt cancelled/invalidated AND no unresolved execution evidence. Preserve existing approve-create path, using same admission and item validation. No second approval of historical sale and no fake reopen.
- Replacement refers to same sale, records predecessor ID, reason, actor and timestamp; old delivery remains terminal with original items/snapshot. New delivery is NEW for management-created assignment, with existing JOB-010 offer/rescue, canonical planned interval and SCH-001 checks. Prefill from approved sale or prior unfulfilled plan (explicitly labelled), manager reviews all quantities. No automatic replacement on cancellation.
- At most one live delivery attempt; if any completed delivery exists, block further linked delivery by default. Cancelled/invalidated attempt with deliveredAt or other physical/stock evidence: block automatic replacement and require explicit reconciliation; never infer goods returned from cancellation/invalidation. No partial deliveries, no remaining stock arithmetic, no fulfillment reversal.
- Use additive migration replacing lifetime index only after invariant analysis (partial active index plus locked sale guard across completed/history; unique predecessor link if suitable). Row lock on source sale serializes late/replace/approve path; canonical lock ordering users→customer→contacts/products→sorted JobCards→intents. Prevent two simultaneous replacements and approval/create race, enforce with database and service where feasible. No migration number reserved; migration 071 immutable.
- Proposed API POST /api/job-cards/:saleId/delivery-attempts with clientActionId, expectedVersion, optional previousDeliveryId+expectedPreviousVersion, reason when replacing, assignee, planned start/end, items and note. Exact field names finalized in FLOW-C. Return authorized created ID and updated sale context; identical retry returns original receipt even if state since changed, after authorized read/replay rules. Distinct payload same key reject; stale states typed 409; unavailable module does not prevent core delivery. Existing approval payload remains compatible; old linkedDelivery reader remains supported (current attempt or final successful attempt, restricted id semantics); additive attempt history projection with authorized pagination.
- If source SALE invalidated: no new attempt; existing physical delivery remains independent; management flags review. If prior delivery already physically fulfilled, no implicit reversal; WH/ACC own correction independently. If no delivery requested at approval, sale stays approved and eligible for late create. New SALE-003 decision explicitly amends SALE-002 §6/Q4 only; no change to agreement count or pair state.

## 4. UI and operational handling
Job detail contains contextual actions and a related-work panel: source, intended next action, target type, current status, owner if authorized, blocked reason, link only if authorized. Proposal card includes purpose, customer, target assignee/date, prefilled product context where allowed, note, manager accept/adjust/reject; rejection reason audit; no hidden auto-create. For sale show no delivery / waiting assignment / scheduled / in progress / completed / cancelled / requires reconciliation; old attempt history clearly labelled. Management exceptions queue deep-links to source/attempt. Mobile keep primary action obvious, no forced back navigation or duplicate form. Realtime scoped projection; messaging optional; no sensitive cross-owner IDs in events.

## 5. Acceptance
Eligible IN_PROGRESS/COMPLETED visit sale paths and standalone preserved; TRAINING permitted only after D05; OTHER rejected; cross-staff pair decoupling and paired submit/approval/rollback unchanged. Same source may create independent allowed demo+training proposals; retry no duplicate; conflicting action IDs rejected; manager cross-staff assignment with JOB-010 guards; staff cannot approve/cancel. Late creation and replacement race (two requests, one winner), completed delivery blocks, physical evidence blocks, terminal source rejects, invalidation no cascade, same-org refs, no reassignment leak. Verify old clients and report projection, migration on existing 071 rows, no stock/financial writes with all optional modules off.
