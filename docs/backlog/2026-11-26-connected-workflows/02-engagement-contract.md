# ENG-001 — Engagement result, interest and follow-up contract (proposal)

## 1. Semantics
Keep SALES_MEETING JobCard and its engagementKind as planned purpose; do not mutate a visit into SALE or reinterpret a historic kind. At execution record separate occurrence (held/not held), commercial/noncommercial outcome, and desired next actions. Planning fields stay separate. Optional actual channel (IN_PERSON, PHONE, ONLINE, OTHER) is an actual-result attribute, not a way to bypass existing location/START policy. If non-field channel needs different START/occupancy behavior, separate explicit decision; no implicit geolocation exception.

Proposed typed vocabulary:
- occurrence: HELD, NOT_HELD; UNKNOWN_LEGACY read-only compatibility for records that cannot be inferred unambiguously. New submissions must be explicit after rollout.
- outcome: INTERESTED, DECISION_PENDING, NOT_INTERESTED, NONCOMMERCIAL_COMPLETED, OTHER; optional for NOT_HELD, no automatic sale outcome from a checkbox. A linked SALE status drives sale indicator independently. Existing outcome stays readable; never map POSITIVE to sold.
- notHeldReason: CONTACT_NOT_AVAILABLE, CONTACT_BUSY, CUSTOMER_UNREACHABLE, REQUESTED_LATER, OTHER; no reason required for held follow-up. Existing unsuccessful reason preserved as historical value.
- next intent: FOLLOW_UP, DEMO, TRAINING, SAMPLE_DELIVERY, SALE, TECHNICAL_REQUEST, NONE; proposal is not execution. Distinct actions may coexist; NONE mutually exclusive with open requested actions; active routine visit cycle cannot silently end.

HELD requires actual meetingAt, summary, result and valid customer/assignee; actual contact optional according to existing CRM rules. NOT_HELD requires structured reason, summary, no fabricated meetingAt/metContact; planned contact remains. Use existing authoritative time tolerance. No retrospective inferred attendance. Draft planning can leave fields null until submit. Approval snapshot includes new semantic fields; revision/withdraw follows existing state machine. Invalidation never rewrites historical facts.

## 2. Follow-up policy
Preserve existing legacy JOB-008 predicate and mapping (FOLLOW_UP_REQUIRED + structured unsuccessful reason → 7 days; POSITIVE → 14 days) until ENG-B activates. For the new model, propose mandatory CONTINUE for routine CUSTOMER_VISIT/FOLLOW_UP with NOT_HELD or HELD/DECISION_PENDING → 7 days, HELD/INTERESTED → 14 days; valid explicit proposed time overrides default. For NOT_INTERESTED, NONCOMMERCIAL_COMPLETED or OTHER require explicit management cycle disposition, CONTINUE uses 7 days if no explicit date, REQUEST_END needs structured reason and manager approval; no automatic closure. Nonroutine kinds opt in, 7-day default when requested absent explicit date (INTERESTED → 14). This is an explicit partial amendment to JOB-008 mandatory predicate/target, JOB-009 continuity and JOB-010 not-held rules, not existing behavior. Keep 15-minute lead, organization timezone, 08–19 auto window and Sunday exclusion, 30-day horizon, SCH-001 occupancy; keep manual overrides and JOB-009 cancellation continuity. Introduce separate routine cycle disposition CONTINUE / REQUEST_END (approved reason) / NOT_APPLICABLE; final policy needs D03 acceptance. Explicit future follow-up is possible after held interested/undecided or not held, irrespective of commercial outcome. Nonroutine demo/sales/training may opt in; no forced cycle by default. Proposed continuation uses existing follow-up proposal/create transaction, not new scheduler. If no free slot, use current manual fallback with a coded next action; don't silently drop commitment. On submit, validate proposal and snapshot; approve creates one routine child atomically; revision/withdraw creates none; replay returns existing child. Manual post-hoc retains current cap until separately amended. Do not equate direct source link and FOLLOW_UP kind.

NOT_HELD with no meetingAt: preserve JOB-010 release 2a (assignment-acceptance-sla.md:586–589) and migration 007 constraint meeting_details_follow_up_check: legacy nextFollowUpAt MUST remain null when meetingAt is null. New typed next-action proposal field proposedFollowUpAt (separate from meeting details next_follow_up_at) can hold an optional future target, including NOT_HELD; this is an explicit JOB-010/JOB-008 extension, not relaxation of the 007 CHECK. Add nullable field through a new forward migration in ENG-B, on the owning proposal/detail structure selected after reviewing existing proposal storage; never edit migration 007 or reuse nextFollowUpAt. HELD retains nextFollowUpAt > meetingAt; new proposal must not contradict it (reject conflicting dual input; derive one canonical target). Validate proposedFollowUpAt against authoritative submission/request time and existing lead floor, recompute at approval per JOB-008; no invented meetingAt or backfill. Legacy clients keep prior payload and default behavior; new clients read typed target separately. At submit preserve proposal in immutable approval snapshot; approval uses proposal target, not fake actual time. An optional attemptedAt is deferred; not-held reporting uses explicitly labelled staff completion-time basis where no actual attempt timestamp exists. Tests: legacy null CHECK still enforced; new NOT_HELD proposal persisted and approved; HELD legacy behavior, expiry, resubmit and replay.

## 3. Structured optional details
Add normalized engagement-product interest rows (organization, job, product, captured snapshot name/SKU/unit, interest category e.g. DISCUSSED/INTERESTED/DEMO_REQUESTED, optional note; no quantity commitment, price or stock). Same org and allowed product; no duplicate product/category, bounded lines (proposed 25), existing catalog selection UI. Capture optional actual channel, standardized commercial blocker (PRICE/BUDGET/COMPETITOR/DECISION_APPROVAL/TECHNICAL_FIT/OTHER), competitor text, expected decision date (local date, not scheduled job), feedback, needs summary. Training fields only when applicable: subject, participant count (nonnegative bounded integer), completion result and optional additional training need. No sensitive patient data, no unnecessary personal detail. Allow empty optional fields; make only minimum submission fields required; mobile progressive disclosure.
