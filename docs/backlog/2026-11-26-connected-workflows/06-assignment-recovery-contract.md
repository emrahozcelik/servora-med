## 2. Product rules
An assignment answer is not a customer job outcome. A declined or released offer leaves the customer's job intact and moves recovery responsibility to management. Distinguish DECLINE before acceptance, RELEASE after acceptance but before START, and CHANGE_REQUEST after START (and any existing permitted pre-start cases). Keep offer state machine and JobCard status vocabulary; do not invent CANCELLED or an unassigned nullable owner state to represent refusal. UI may say "Görevi yerine getiremiyorum" with explicit current consequence, or "Değişiklik talep et" for a request that does not release the assignment. Do not hide the distinction from staff. No automatic acceptance, cancellation, or transfer on refusal. Existing deadline and urgent-offer safeguards are not bypassed.

## 3. Staff form and proposal semantics (RESCUE-002)
Reason and proposed solution are separate typed fields. Preserve existing reason codes and historic text; keep separate assignment-answer and change-request vocabularies/DB CHECKs. Align shared meanings and labels, not lifecycle or types: OUT_OF_TOWN is a new assignment-answer reason; reuse literal CUSTOMER_POSTPONED from change requests and WRONG_PRODUCT (existing label covers wrong product or record details) as additive assignment-answer values if accepted. Do not invent INCORRECT_JOB_DETAILS or a second synonym; retain MISSING_STOCK_OR_EQUIPMENT in both; splitting deferred. Existing change-request codes unchanged; no reinterpretation of OTHER. Explicit JOB-010 amendment and additive assignment-offer CHECK/API/UI migration if codes widened. Do not require private medical/leave details or current location. Explanation remains mandatory, bounded using existing reason limits. Suggested solution enum (names provisional): RESCHEDULE_SELF, REASSIGN, CORRECT_DETAILS, CANCEL_REQUEST, MANAGEMENT_DECIDES. Suggestion does not authorize target mutation. A staff member need not name another staff member. May suggest earliest available date/time or explicit start for RESCHEDULE_SELF; proposed default single concrete future start, duration derived server-side. Extend JOB-012 to allow optional alternate time for appropriate reasons (city-out/leave/distance, customer postponed, etc.) independent of reason; when RESCHEDULE_SELF chosen, valid start required. Existing SCHEDULE_CONFLICT legacy request remains accepted with its required time; new client may explicitly indicate cannot suggest a time / reassign, subject to accepted amendment. No proposed time if not proposing RESCHEDULE_SELF; legacy payload compatibility with clear mapping. Confirm exact code/reason compatibility before migration. No treating a date in free-text as a binding commitment.

Preview schedule and slot suggestions with canonical SCH-001 occupancy, customer scheduling/frequency rules, authoritative time, existing 15-min lead where applicable and human-choice hours. Proposed date does not reserve slot. On manager acceptance recheck latest offer, proposer still assignee/active, planned duration/version, same-org customer, future interval, occupancy and deadline policy under locks. JOB-012 explicit confirmation for an actual staff-proposed interval accepts the job without second staff acceptance; manager-selected different interval sends new offer, not implicit consent. If proposal expires/conflicts, show alternative times or reassign, retain historical proposal. Do not use browser clock as business authority. Replays after date passes still return prior committed receipt with current-state distinction.

## 4. Manager recovery decision form (RESCUE-003)
One entry "Görevi çözüme ulaştır" from detail and queue. Show current job/customer/type, existing priority, planned interval, time until appointment/end, original assignee, latest offer/change-request facts, reason/explanation and staff suggestion, whether appointment is fixed/at risk, open downstream links and appropriate permission-filtered facts. Default recommendation deterministically based on reason, recorded priority, actual server-time risk and availability. A UI scenario selector is not persisted priority unless manager explicitly edits it with existing permission; no artificial urgency or location inference. Use same detail/context from server; unavailable actions explain why. All critical actions have a consequence preview, confirm, pending, committed receipt and durable result per [07](07-manager-action-feedback.md).

| Action | Admission and effect |
| --- | --- |
| ACCEPT_PROPOSED_TIME | latest valid staff proposal + current version; existing JOB-012 command; move same card and accept for proposer atomically. |
| RESCHEDULE | same card, eligible pre-start lifecycle, different interval chosen by manager; existing assignment offer producer opens new offer; no autoaccept. |
| REASSIGN_KEEP_TIME | eligible pre-start card, valid new staff at existing interval; preserves customer appointment, opens new offer. If passed start/end or short notice, show canonical acknowledgement/reschedule requirements. |
| REASSIGN_AND_RESCHEDULE | one transaction, not sequential UI requests; validate target staff and new interval together, update history and one offer. |
| REOFFER | same staff/time if eligible, no automatic repeated offer after refusal; make explicit. |
| CORRECT | purpose-bound supported field change, versioned; where actual correction resolves a change request, bind evidence atomically. If no canonical mutation exists, explicit truthful record-only acknowledgement, not fabricated correction; see OVR-7 guard below. |
| CANCEL / REPLACEMENT | manager only; JOB-009 follow-up continuity RESCHEDULE replacement or END_CYCLE with structured reason; preserve original linkage; if same-card reschedule is possible prefer it; no duplicate follow-up. SALE-003 owns delivery replacement. |
| REJECT_CHANGE_REQUEST | manager only with explanation; request closure is not assignment acceptance, cancellation or completion. |
| STARTED_CASE | no default pre-start transfer/reschedule or rewriting startedAt; existing management lifecycle restrictions, correction/linked successor/cancel under explicit contract, preserve evidence; no new START by manager. |

Use existing named command services, validated PATCH and 049 receipts, not a competing workflow engine. Introduce thin purpose-bound recovery API/transaction orchestration only where necessary; no generic arbitrary transition endpoint. Proposed input: jobId, expectedVersion, expected latest offerId/version or changeRequestId, clientActionId, action-specific payload, reason/acknowledgement when required. Server returns committed result with applied action, job status, changed interval/assignee, offer state, resolved request and authorized successor IDs only when applicable. A newly sent offer means awaiting staff response, not completed recovery in delivery sense. Distinguish decision taken, assignment accepted, work executed. Old offer/request cannot overwrite a newer one; first competing manager wins, second refreshes with conflict. Lock users/customer/other refs/job/intents per current order; all writes incl audit, schedule revision, new offer, request resolution and relevant notification/event commit together. Same-key same-payload replay returns receipt; changed payload rejected. No network in lock, no premature notifications. Use existing role/org/action checks. For record-only closure require accurate label and explicit reason, never display "iş düzeltildi" if no mutation. OVR-7/lateness-reports.md:142–148 currently qualifies CORRECTED, RESCHEDULED and LINKED_JOB_CREATED by code alone (and qualifying management CANCELLED). Do not introduce new record-only uses of these qualifying codes. New RESCUE-003 neutral ACKNOWLEDGED_ONLY (provisional name) closes request without claiming correction and must be excluded from OVR-7 qualifying predicate; explicit JOB-010/OVR-7 amendment, enum/CHECK/API/read tests in same slice. Reserve qualifying codes for verified canonical mutation/evidence in new form, existing historic rows/classification unchanged; no retrospective reclassification or rewriting accountability. REJECTED remains distinct. If neutral code not yet accepted, keep request open or existing authorized rejection rather than silently mark corrected. Test linked sale pair or follow-up lineage and physical delivery evidence; preserve existing owner constraints.

## 5. Availability, risk and occupancy (RESCUE-004)
Offer manager both a fixed-appointment staff candidate list and earliest slots for same staff or chosen other staff, using canonical available-slots and occupancy (JOB-011/012, SCH-001). Active eligible same-org Staff only; consider manual calendar blocks only when Calendar contributes, existing core jobs always per accepted policy, customer visit frequency advisory, applicable offer window. List why candidate is unavailable; label counts as scheduled load not productivity, no invented travel distance/territory/skill/leave data. Region/skills/leave data only when authoritative and permission-scoped; absent data means unknown, not suitable by assumption. Candidate results bounded/paged with deterministic ranking (e.g. available at requested interval, nearest alternative slot, scheduled workload then stable ID); no automatic assignment, no guarantee until server validates. Module off still core check.

Proposed occupancy change (requires explicit SCH-001 amendment in RESCUE-004): separate customer appointment risk from staff reservation. Keep OPEN answerable offers and ACCEPTED/started occupancy; consider releasing staff time for latest explicit DECLINED/RELEASED on NEW job, keeping customer appointment and management queue. Decide EXPIRED, WITHDRAWN window passed, legacy/no-offer, urgent OPEN and rollback flags explicitly; default conservative until accepted. No release on a mere change request. Reoffer/transfer atomically reclaims interval or rejects overlap. Audit every occupancy consumer (create, reschedule, available slots, follow-up auto-scheduler, offboarding, Calendar manual entry, sale approval delivery). Test decline + concurrent new job, reoffer conflict, stale/expired offer worker, no-offer legacy, module off; avoid duplicate rule copies. Do not change report/OVR evidence or historical assignment because current reservation changes. If release unsafe, retain existing occupancy with explicit UI reason until policy solved.
