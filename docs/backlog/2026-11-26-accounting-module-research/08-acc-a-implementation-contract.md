Date: 2026-11-26. Status: **proposed for owner acceptance**, not authorization to code or deploy. Owner requested closing the outstanding contract gaps; the choices below are the proposed defaults for the first slice, not claims about actual pilot practice. ## 1. Scope and release boundary

One vertical slice: default-off ACCOUNTING runtime state, finance permissions, outbound external invoice-reference ledger, many-to-many operational source links, audited corrections and reconciliation view. A reference is informational, not evidence of statutory issuance, outstanding balance, payment, full invoicing or stock movement. This is a limited internal/pilot milestone, not the complete saleable Ön Muhasebe module. No price, VAT, currency, amount, due date, internal/official document numbering, purchase/supplier, receivable/payment, PDF, attachment/URL, export, connector, worker, alert, legal issuance or backfill. The wider ACC-3–7 target remains unchanged. No new job type, generic RBAC, event bus or dependency on other optional modules.

## 2. Runtime state and operator contract (D16)

- Registry: ACCOUNTING, label "Ön Muhasebe", authenticated capability accounting (installation enabled, not personal finance authorization). Add explicit default-off initialization descriptor, distinct from legacy env takeover; no ACCOUNTING_ENABLED. Preserve current Overview and other module semantics. Extend closed constraints additively with source DEFAULT_OFF and SYSTEM event MODULE_STATE_INITIALIZED (old value null, new enabled false, source DEFAULT_OFF); extend module event shape and initialization lookup/index. Validate actor/source vocabulary in schema/service. Existing 074 is immutable.
- In API startup after schema verification and before listen, insert missing ACCOUNTING row at version 1 false plus exactly one initialization audit event in one transaction; concurrent startup only winner audits. If row missing but initialization or any prior module-state event exists, rollback and stop startup; no reset/re-derive. No automatic enable on new install/upgrade/restart. Existing row unchanged. No migration number reserved.
- Reuse GET /api/operator/modules and PUT /api/operator/modules/ACCOUNTING with existing expectedVersion and operator session checks. No new capability beyond MODULE_MANAGEMENT. Current version+same value is no-op; stale version always 409. Operator confirmation states records retained and access blocked; no finance counts/content required. No customer can toggle.
- Authenticated customer: known disabled -> 404 NOT_FOUND on every accounting endpoint, including grants; unreadable/missing state -> 503 ACCOUNTING_STATE_UNAVAILABLE, capability false and sanitized log, never env fallback. Invalid session -> established 401; when enabled, lacking relevant permission -> 403 FORBIDDEN; out-of-org resource -> indistinguishable 404 for authorized caller. No accounting outage may stop unrelated Core endpoints. No module-state caching.
- Read-only operations may complete if admitted before disable/revocation (as MOD-002 Overview); no new reads admitted afterwards. For mutations and replays use transaction admission in §5. Responses are not cacheable (Cache-Control: no-store); clear module state, reference data and pending response application when capability or authorization changes. Do not claim instantaneous remote-tab notification: next focus/revalidation/request enforces the new state. No new polling/worker/SSE required.
- Disable/re-enable retains reference and grant history exactly, no automatic replay, backfill, reminders or financial effect. Backup/restore restores state at backup instant, never forcibly enables; pre-introduction backup initializes disabled after normal upgrade; MOD-002 operator reset unchanged.

## 3. Authorization (D9/D17)

Only active ADMIN and MANAGER customer accounts may receive finance rights in ACC-A. STAFF has no finance API/data/status, even on own jobs; existing operational note access unchanged. Operator has no customer finance access. ADMIN may administer grants without business-data access; neither role has implicit finance read or write. Explicit self-grant by an active ADMIN is allowed (bootstrap and recovery), with confirmation and audit. No mandatory second admin: small single-admin installation must be usable. ADMIN alone can grant/revoke for active ADMIN/MANAGER in same organization. No shared login or extra role.

| Capability | Meaning |
| --- | --- |
| REFERENCE_READ | list/detail, customer/source picker, reconciliation and reference audit |
| REFERENCE_WRITE | create and add source links; requires READ |
| REFERENCE_CORRECT | correct, remove/review link, void, replace, reopen; requires READ and WRITE |

Represent the three supported capabilities in one typed module grant row per (organization_id,user_id) with flags/read-write-correct dependency CHECK, grant version, bound user version, grant actor and time. No generic string/JSON permission store. No grants on migration. Initial no-row expectedVersion = 0; each actual grant/revoke changes grant version; same-version exact no-op creates no extra audit; stale version conflict even for same desired values. Revocation retains versioned row with false flags and audit. Bind grant to existing users.version at time of grant, plus active management role. Current People repository increments version on role/active/name changes. Any user version change invalidates the grant until explicit re-grant (including harmless name changes: deliberately conservative first-slice tradeoff, displayed as "Yeniden yetkilendirme gerekli"). Revalidate all current auth/People user-version writers at implementation; if lifecycle changes do not reliably increment version, stop and address with minimal accepted lifecycle contract, never permit stale privilege resurrection. No dependency on module-on in Core lifecycle. No automatic regrant after deactivation/reactivation or role change. A new grant explicitly binds current version and is audited even if flags unchanged. Historical grant actors are retained; no silent privilege recovery.

UI: ADMIN grant administration entry under Ön Muhasebe even if lacking READ; MANAGER sees module only with effective READ. ADMIN can grant self, cannot read references until granted. Use typed effective personal finance capabilities separately from installation boolean (e.g. accountingAccess { manageGrants, readReferences, writeReferences, correctReferences }); compute server-side at login/me, all false on disabled/unreadable grant state, manageGrants true for active ADMIN only while state enabled and readable. Grant-read failure fails closed for accounting routes (503 ACCOUNTING_ACCESS_UNAVAILABLE), does not log out Core user. Use no permission data in operator APIs. No financial field in Core JobCard/customer DTOs. No global finance search or operational reports.

## 4. Reference identity and lifecycle (D3/D5/D6/D15)

### Issuer and number
First slice records outbound invoices of exactly one legal issuer per organization (the organization itself); issuing software is metadata, not identity. No inbound/supplier, multi-legal-issuer or connector namespace. If actual pilot has more than one issuer per org or numbers that cannot fit this rule, stop for explicit extension before real data entry. Identity namespace is (organization_id, outbound, normalized_number); outbound is implicit in ACC-A, later widening requires accepted migration preserving current identities. No year added: official/external number must itself be unique for this issuer. Store original trimmed number, 1–100 ASCII characters, starts with alphanumeric, subsequent characters alphanumeric or . / _ - ; no whitespace within, no Unicode/confusable rewriting, normalization ASCII uppercase only, punctuation preserved. Reject invalid rather than silently modify. Examples: " abc-01 " and "ABC-01" collide; ABC-01 and ABC01 differ; same number different organization allowed. Preserve original case on display. Pilot must confirm namespace/format before production pilot; synthetic tests do not require an ERP selection. An optional ETTN UUID field is a second organization-scoped unique identity (when present); not verified by Servora. No arbitrary external ID or URL in A. Source system enum LOGO, NETSIS, MIKRO, PARASUT, E_DOCUMENT_PROVIDER, OTHER, UNKNOWN; informational only; system change never changes uniqueness. No VKN/TCKN snapshot in A. Invoice date ISO YYYY-MM-DD valid date, not after today's organization business date (reuse existing business-time/date policy, no new timezone setting); date is date-only; no implicit JS timezone conversion.

### Record and links
Header: required customer in same org (historical/inactive customers can be referenced), immutable customer name snapshot, issuer namespace implicit, invoice number original/normalized, invoice date, optional ETTN, source system, optional bounded non-sensitive description, status RECORDED/VOID, version, actor/time. No status INVOICED/PAID. Zero source links allowed. Only COMPLETED same-customer same-org SALE or PRODUCT_DELIVERY with at least one actual SALE-purpose line can be newly linked. Delivery with mixed purposes may be linked but implies no quantity coverage. SAMPLE/CONSIGNMENT/RETURN/OTHER-only delivery not eligible; other source types not eligible. If invoice precedes approval, record standalone and attach once source is eligible; don't block ordinary invoicing references on operational approval. No cross-customer group invoice in ACC-A. Use explicit source choice; never auto-add related sale/delivery. Many references per job and many jobs per reference; no unique job-only constraint. Preserve current SALE-002 one-delivery-per-sale policy (multi-reference link does not change physical delivery rules).

Association retains source version, type, title and customer snapshot at link/review, active flag and actor/time. Unique pair reference+job; add same active pair -> 409 ACCOUNTING_LINK_EXISTS (exact same clientActionId replays), inactive pair can be reactivated by CORRECT with reason and new eligibility check. Remove/review uses audited versioned command, no hard delete. For linked job changes, derived reconciliation state: SOURCE_CANCELLED_OR_INVALIDATED (highest precedence), SOURCE_CUSTOMER_CHANGED, SOURCE_NO_LONGER_ELIGIBLE, SOURCE_VERSION_CHANGED, CURRENT. Compare current Core facts to captured snapshot; no Core callback, no auto-void. Authorized review of version change may refresh snapshot only if still eligible and same customer; old snapshot retained in audit. Otherwise remove link with reason or retain flagged history; never silently mark resolved. A void reference retains all links/history and is excluded from active-reference presence. Current links count as references only, never full invoice coverage. Worklist is neutral "Referans kaydı bulunmayan işler", eligible COMPLETED sources with no active recorded reference, filtered by customer/date/type; no 7-day cutoff, no overdue label, no automatic alert. Distinct source IDs avoid duplication from multiple links; references counted by header identity, not summed over joins.

### Changes and correction
Every mutation uses expectedVersion for existing aggregate and mandatory clientActionId; all modifications bump header version once and commit one structured event per affected aggregate. WRITE creates or adds new eligible links; CORRECT handles any existing metadata/identity correction, removal/review, local void and reopen. Require trimmed reason 1–500 chars for corrections/void/reopen; no sensitive identifiers in free text. Preserve history, no physical delete. Metadata/date/customer/ETTN correction uses same identity only if normalized number unchanged, with audited old/new values; changing customer requires zero active links or explicit atomic removal of all active links, no implicit reassignment. Case-only number correction may update display value with audit. Changing normalized number requires atomic replacement: reserve old identity as VOID with explicit successor ID, create new RECORDED reference and explicit selected valid links; carry no implicit source/financial facts. Replacement points back to old reference (one-to-one lineage; no cycles); old row is never deleted or silently reused. A voided identity without successor may be reopened only by CORRECT, reason required, after current identity/link validation; all ineligible active links must be explicitly removed in same command or reopen rejected. Wrong capture of ETTN corrected with audit and uniqueness check; historical values in audit, no automatic external verification. Same ETTN across predecessor/successor on number correction: explicitly transfer current ETTN claim in same transaction and preserve historical ETTN in old event; no two active claims. Number uniqueness includes VOID, so a duplicate real identity never creates a second header. Reject replacement to an existing identity (including VOID); use authorized review/reopen of that existing record separately rather than automatic merging. A local void/reopen changes only Servora reference state, never external invoice validity. Reversal is local reference correction only, not future payment reversal.

Legacy job_card_notes.invoice_number API, UI entry, history and replay remain byte-for-byte unchanged on/off. Authorized users may see a separate reference section/link on relevant Core detail, fetched by accounting API; never require finance workflow for notes. No copying old records or receipts, no auto-linking.

## 5. Transaction, concurrency, idempotency and audit

Source inspection at original base: runCriticalAction in server/src/db/critical-action.ts starts a transaction, claims processed_actions, and returns completed replay **without invoking work**; therefore placing a guard only in work is unsafe. Add the smallest opt-in pre-claim transaction admission callback (same PoolClient, before any receipt INSERT/SELECT), or equivalent narrowly scoped refactor retaining existing helper behavior for every old caller. Test both work and replay paths; don't introduce a duplicate generic receipt implementation. Preserve request hash semantics and existing 200/replay/409 ACTION_IN_PROGRESS, CLIENT_ACTION_REUSED and bounded 503 uncertainty retry contract. Return only minimal mutation receipt {id,version,status} (grant commands target id/version), no invoice numbers or sensitive audit payload in processed_actions. Same operation key per command type; hash includes canonical target, expectedVersion, normalized data, explicit source IDs sorted, reason and display number (if changing display). Same key + changed payload -> 409; same request after response loss -> identical minimal response only if currently authorized and module on. No replay of external effects. Failed validation or denied admission leaves no receipt.

Order for accounting mutations: BEGIN -> ACCOUNTING state FOR SHARE -> relevant users rows FOR SHARE (actor plus grant target, sorted IDs; grant changes use target FOR UPDATE, acquire strongest needed lock once) -> grant row FOR SHARE for business write/replay or FOR UPDATE for grant mutation -> receipt claim/replay -> header(s) FOR UPDATE sorted -> customer/source rows FOR SHARE sorted -> domain/audit/receipt completion -> COMMIT. Check session, active role, current user version and grant after locks; revalidate actual session expiry/revocation using existing auth repository on same client; lock session row against revocation where existing auth lifecycle permits, align current user/session ordering. Inspect current Core and operator lock order, including People deletion and job mutations, before implementing; no incompatible global lock order, never hold a network call under transaction. Operator locks operator account then module row FOR UPDATE; no path takes customer lock then module row in Core. Shared module row lock conflicts with toggle and is held through commit. Grant change target lock serializes absent grants as well as existing rows; lock user version also against lifecycle updates. If current source implementation has different lock order, document safe adjustment preserving invariants; no bypass. Bound transaction/lock time using existing critical-action timeout conventions (determine actual settings from current main), map lock/deadlock/serialization failures to existing retryable contract; uncertain commit retry same ID. Real PostgreSQL two-session barriers test both orders (write vs disable, replay vs disable, grant revoke vs write/replay, role/deactivate vs grant/write, source change vs link, duplicate identity/ETTN), timeout and rollback. After disable commits no new financial write or admitted replay with stale enabled state; previously admitted work serialized before disable may complete. After revocation commits no stale permission write/replay. No guarantee that data already delivered to a browser can be erased.

Use module-owned append-only acct_reference_events and acct_grant_events (or a single typed module event table with explicit subject/actor CHECK and composite org FKs). Fixed event vocabulary: REFERENCE_RECORDED, REFERENCE_CORRECTED, SOURCE_LINK_ADDED, SOURCE_LINK_REMOVED, SOURCE_LINK_REVIEWED, REFERENCE_VOIDED, REFERENCE_REOPENED, REFERENCE_REPLACED, FINANCE_GRANT_CHANGED. Audit includes actor, org, UTC instant, action ID, aggregate version, reason, structured changed fields and immutable prior snapshot; redact personal identifiers, no credentials or free-form secret dumps. Grant audit ADMIN-only; reference audit READ only. Event insertion and receipt completion atomic; audit never exposed to operator or logs. No cross-org identifiers echoed. Authorization before resource existence disclosure. Failure to read state/grant is coded 503, not silent fallback.

## 6. Schema and API checklist

Additive migration chosen against exact current main. Widen existing module registry, source and audit checks and indexes; no historical edits. Proposed module tables: acct_finance_grants, acct_invoice_references, acct_reference_sources, acct_reference_events, acct_grant_events. Composite (organization_id,id) FKs for customers, users, sources, headers and lineage; RESTRICT history, unique normalized number across states, unique non-null ETTN current claim, pair uniqueness, version/status/time/actor CHECKs, appropriate organization-first indexes for lists and reconciliation. Use SQL and service checks for cross-table type/customer/status; lock and validate, not merely FKs. Existing Core hard-delete behavior must map new history FK to existing coded blocker in both states; no hard-deletion of actor/financial history. Grant-only user deletion semantics must not silently lose audit; if necessary return existing history blocker consistently, not new offboarding blocker. Regular user deactivation remains possible. Demo dataset: register exact dependency/ownership or explicit fail-closed blocker for affected dataset before purge, no silent cascade or orphan; no new accounting demo generator. No financial fields in Core tables or DTOs. Existing migrations/backup inventory and schema health expectations verified.

Use existing paginated contract (default 6, canonical query, stable order with id tie-breaker), bounded search and source selection (max 100 links per request and active per reference in ACC-A, no unbounded audit arrays), strict body schema, trimmed bounded strings, UUID validation, existing error envelope. Unknown extra keys rejected; org and actor taken from session only. Invalid input 400, resource not found 404, stale header or grant version 409 ACCOUNTING_VERSION_CONFLICT, identity conflict 409 ACCOUNTING_REFERENCE_EXISTS, wrong same-org customer/type/state 409 ACCOUNTING_SOURCE_INELIGIBLE, duplicate pair 409 ACCOUNTING_LINK_EXISTS; no raw SQLSTATE. For same-org ineligible source return no other customer detail. Existing retry/401/403 conventions retained. Details use minimal field projection and stable pagination. Use existing customer picker if authorization permits, otherwise scoped accounting picker; no broadened Core CRM access.
