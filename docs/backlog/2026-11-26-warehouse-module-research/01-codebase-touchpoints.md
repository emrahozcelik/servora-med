## How to read the verdicts

| Verdict | Meaning |
| --- | --- |
| **Core keeps** | Stays in `server/src/modules/job-cards` / `products` / `people` / etc. Warehouse reads it, never writes it. |
| **Warehouse owns** | New tables/rules that only the Warehouse module should write. |
| **Shared contract needed** | Both sides write or both sides read with a semantic agreement; needs an explicit port + a decision record before code. |
| **Not touched** | No change required for the Warehouse module. |

## Risks

1. **Vocabulary churn (high).** `job_card_activity_logs_event_type_check` has been rewritten in **13** migrations (33 `DROP`/`ADD` lines). If stock events land there, every future module pays that cost again. *Mitigation:* Warehouse-owned event table (H6).
2. **Sharpest policy conflict (high).** DOM-001:351 says `CONSIGNMENT`/`RETURN` "do not create stock movements"; MOD-001:2022–2028 gives Warehouse "returns and corrections". Both are Accepted. A module that auto-creates movements for `RETURN` contradicts DOM-001; a module that refuses contradicts the module's purpose. **This needs an explicit decision, not an implementation choice.**
3. **Quantity-domain mismatch (high).** `job_card_delivery_items.quantity` is `NUMERIC(12,3)` with integer-only API input (`delivery-input.ts:22–38`), while `job_card_sale_items.quantity` is forced integer (`058:21–23`). A stock ledger with fractional units will not reconcile against either.
4. **Timestamp ambiguity (medium).** Three candidate "delivery happened" times exist: `delivered_at` (business), `staff_completed_at` (submission), `manager_approved_at` (approval). DOM-001:357 and DOM-006:633–634 say `delivered_at` is the real delivery time; reports use it. The stock `occurred_at` should be decided once.
5. **Silent offboarding hole (high).** Both the delete-blocker query (`people/repository.ts:252–305`) and the offboarding mutation list (`offboarding.ts:526–706`) are hand-enumerated. A stock table is invisible to both; the failure mode is a *silent* dangling reference, not an error.
6. **Silent demo-purge failure (high).** Same hand-enumeration in `analyzer.ts`; the analyzer's own comment (`:558–569`) documents a past `FK 23503` incident caused by exactly this.
7. **Restore "succeeds" with an empty ledger (medium).** `CORE_RELATIONS` (`restore/postgres.ts:11–25`) does not know Warehouse tables; only the ledger hash is verified.
8. **Module-registry CHECK + CI coupling (medium, mechanical).** `074:59`/`074:86–87` and `verify-env-examples.sh:40–50` both fail loudly. That is good — but it means one "module exists" PR touches **five** files outside the module (registry, migration CHECK, capabilities both sides, two env examples).
9. **Product-delete drift (medium).** Documented "no DELETE endpoint" vs. implemented physical delete (`API draft:489–490` vs `products/routes.ts:19`). A warehouse FK makes this drift operationally dangerous.
10. **Core service size (medium, not a blocker).** `job-cards/service.ts` is 9,489 lines and `repository.ts` 7,485. Adding hooks H1/H2 inside `runLifecycle` increases an already large surface; the port must be one call site per path, not a branch sprinkled through the finalize transaction.
11. **`installation_module_state` "off" is not "no data" (medium).** Turning WAREHOUSE off after movements exist leaves rows behind; unlike Overview there is no neutral state. Needs an explicit rule (read-only? hidden but authoritative?).
12. **Single stock source of truth (high, but a decision not a code risk).** MOD-001:2029–2031 requires the authority to be declared per deployment. Nothing in the code can enforce "external ERP is authoritative" — it must be a declared mode, surfaced in the operator UI.

## Open questions for the owner

1. **Does the Warehouse module create movements for `RETURN` / `CONSIGNMENT`?**
   DOM-001:351 says no; MOD-001:2022–2028 assigns "returns and corrections" to Warehouse.
   - (a) Keep DOM-001 literally: `RETURN`/`CONSIGNMENT` stay classification-only, stock ignores them. *Recommended for slice 1* (smallest honest slice, no contradiction).
   - (b) Warehouse overrides for `RETURN` only, via a new decision record that explicitly supersedes the DOM-001 sentence.
   - (c) Model returns as a separate Warehouse "return receipt" flow that references the delivery item but is **not** inferred from `delivery_purpose`.

2. **Which timestamp is a movement's `occurred_at`?**
   - (a) `job_card_delivery_items.delivered_at` (business time, used by reports). *Recommended.*
   - (b) `manager_approved_at` (approval time).
   - (c) An operator-supplied movement time, defaulting to (a).

3. **When does stock move for a SALE-002 delivery — at card creation or at delivery completion?**
   `createSaleApprovalDelivery` creates a `NEW` delivery card (`service.ts:2863–2873`); the goods are not delivered yet.
   - (a) **Reserve** at creation, **deduct** at `PRODUCT_DELIVERY` completion (hooks H2 then H1). *Recommended.*
   - (b) Deduct at creation only (simple, but books stock out before anyone drove to the clinic).
   - (c) Deduct at completion only, no reservation (no protection against over-committing).

4. **Is `products.unit` allowed to become the stock unit?**
   DOM-004:550 says unit is informational with no invented default.
   - (a) No — Warehouse stores its own unit + conversion; `products.unit` stays a display string. *Recommended.*
   - (b) Yes, with normalization + a new decision superseding DOM-004:550. (Larger blast radius: reports group by nullable unit today, DOM-006:634, 638–639.)

5. **Quantity domain: integer, or `NUMERIC` with explicit unit?**
   SALE is integer-forced (`058:21–23`); delivery is fractional-in-DB/integer-in-API.
   - (a) Warehouse owns `NUMERIC(p,s)` + `unit`, deliveries are **declared** not authoritative. *Recommended.*
   - (b) Integer units only (matches operator reality for "kutu/adet", breaks liquids/partial).

6. **Does the operator see an "external ERP is the stock authority" mode in slice 1?**
   MOD-001:2029–2031 requires an explicit mode per deployment.
   - (a) Yes, as a read-only indicator in slice 1, enforced in slice 2. *Recommended.*
   - (b) No, document it and add the mode when integration exists.

7. **Warehouse audit: shared `audit_events` or its own table?**
   - (a) Own table (`warehouse_audit_events`) + a read port for the JobCard timeline. *Recommended* (avoids the 13-rewrite CHECK pattern).
   - (b) Extend `audit_events` subject/event CHECKs (one more Core migration, but one audit search surface).

8. **Does a user with stock responsibility block offboarding, or is it transferred?**
   Weekly reports already block (`offboarding.ts:1050–1072`).
   - (a) Transfer (vehicle stock reassigned) with a mandatory decision per responsibility. *Recommended.*
   - (b) Block until the stock is zeroed/handed over.

9. **Multi-depot in slice 1?**
   - (a) Two depot kinds only: `CENTRAL` + `VEHICLE` (matches "depots and vehicle stock" in MOD-001:2022). *Recommended.*
   - (b) Arbitrary depot tree (bigger schema, bigger UI, no current consumer).

10. **Where does the first Warehouse UI live — new top-level nav entry, or inside `/products`?**
    Mobile bottom nav is capped at 5 slots (`navigation-model.ts:54`, UI-004 rationale `:118–120`).
    - (a) New top-level entry, hidden when capability off. *Recommended.*
    - (b) A "Stok" tab inside the product page (fewer nav slots, hides the module from operators).
