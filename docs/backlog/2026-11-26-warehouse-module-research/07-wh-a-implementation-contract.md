## 1. Runtime module and authority

Descriptor WAREHOUSE, warehouse capability (required boolean, default false), legacyEnvKey=null, Turkish description/whenDisabled/preserved. State initialized OFF by existing MOD-003. Only installation operator toggles; customer ADMIN manages organization-local warehouse configuration, never operator access. Routes under /api/warehouse; authenticated server checks role and org on every request, known off 404, missing/unreadable 503 MODULE_STATE_UNAVAILABLE, auth capability false on unreadable, no env fallback. Menu and deep links gated; clear module query/cache and close open mutation forms after state refresh/404/503. No promise of erasing already delivered browser data. No placeholder feature or registry entry without usable scope.

Installation state is availability, not verified stock. Proposed readiness generation: reuse the enabled installation_module_state.version as generation ID; operator actual changes increment version, same-value update does not (operator/repository.ts updateModuleEnabled). No extra copy of module enabled or toggle timestamp; no operator-to-Warehouse write hook. Per organization, location and product verification row references enabled generation (and verified count evidence), not a global active flag. No count automatically confirms an omitted product. Derive DISABLED, SETUP_REQUIRED, ACTIVE within verified perimeter, RECONCILIATION_REQUIRED for previously verified but stale generation. A mixed board explicitly shows verified/unverified counts and freshness, never a global assertion that all stock is verified. When a new product/location has never been counted it remains UNKNOWN even when peers are active. Missing data is not zero; a posted zero count is valid verification.

After a disable/enable cycle retained balances remain historical until a fresh count per relevant key under new generation; no backfill or automatic reset. Recount compares physical amount against retained ledger balance and appends adjustment (may be zero); verified zero requires explicit line. Enable/disable itself never changes ledger. A prior generation's count cannot grant current readiness. Only verified sources/destinations participate in normal movements; initialize an empty destination with explicit zero count before transfer/receipt. During unready state only setup, count/reconciliation and read of clearly labeled historical data permitted. Initial or resumed count must reflect physical stock, not assume old balance is current. Before WH-004, no automatic Core stock posting exists; UI states that other operational events do not update stock. WH-004 must add durable pending-delivery/count coverage and exceptions before that integration is enabled.

## 2. Domain and data invariants

Use module-owned locations, stock_movements (append-only), stock_balances (same-transaction derived projection), immutable count/transfer/receipt/correction command headers and line evidence as needed (avoid generic voucher engine), readiness evidence and warehouse audit. Concrete table/column names, types and indices must be reviewed against current schema; no speculative generic framework.

- All business rows scoped by organization_id; composite same-org FKs for product, user, location and movement/source references. Product remains Core catalog identity, not a second product master. Distinct immutable stock identity; first slice supports whole-piece untracked products only, with explicit module-owned per-product eligibility/policy. Do not infer tracking requirements from SKU or empty metadata. Unknown or lot/serial/SKT-required policies not admitted to untracked stock operations; no regulated-product rollout until WH-005. Future key extension must preserve movement history and reconciliation; no fake lot/serial placeholders or aggregate-only traceability claims.
- Location types DEPOT (including main/secondary) and VEHICLE; unique normalized code within organization; one vehicle location per eligible staff for this slice unless explicit subsequent contract; owner active BUSINESS for assignment. Location IDs immutable; deactivate rather than delete; no deactivation with nonzero stock or unresolved exceptions; inactive former owner location is recoverable source-only, never automatically moved or written off.
- Signed movement kinds initial OPENING/COUNT_ADJUSTMENT, RECEIPT, TRANSFER_OUT/TRANSFER_IN, CORRECTION_IN/CORRECTION_OUT. Zero movement not allowed; zero count line retained separately. Each movement has org, stock identity, location, signed delta, server posting instant, actor, action/source reference, reason and immutable source snapshot. Transfer two opposite movements with same immutable group/line identity, same product/quantity, distinct locations; commit all or none. Count header/lines preserve observed quantity, before quantity, difference, count server instant, generation; record zero diff even without movement. Receipt captures supplier/document reference as informational (no finance side effect), physical receipt date and positive units. Correction requires reason, evidence/source link if correcting earlier entry, and positive quantity with explicit direction; never UPDATE/DELETE movement. A duplicate correction of the same error must be prevented through explicit resolution uniqueness; normal later independent corrections remain possible.
- Amount inputs are integer pieces, positive for receipt/transfer/correction, nonnegative for count; use DELIVERY-QTY-001 max 999999999 per input, reject unsafe numeric conversion/overflow, aggregate balance may exceed one input and needs bounded safe DB/DTO representation (proposed BIGINT with explicit JS safe-integer bounds, never silently truncate). One canonical product per line per command, duplicates rejected. Server validates dates and identities; distinguish actual event time from server commit/posting instant; future actual date rejected, count effective instant is server-controlled under locks; no backdated count. Delayed count evidence must be recounted rather than timestamp-rewritten.
- Ledger sum equals projection for every stock key; no negative balances. Establish missing balance key with zero only as internal transactional row initialization, not proof of verified physical zero. Count is the sole initial verification in WH-A. All writes/audit/receipts atomic; no repair by editing balance. Sort multi-row locks by stable keys. Restrict DB writer surfaces; verify immutability by tests.
- BUSINESS actor, location owner and product only; reject DEMO users/products in all commands, no demo row/foreign reference; read access must not disclose real stock to demo users. Product/user hard deletion blocked by all real warehouse business/audit history even when disabled; preflight and FK race map to existing 409 vocabulary, not 500. Include location owner, movement actor and command/audit actors; preserve snapshots through offboarding. No new demo purge dependency unless actual demo stock separately authorized.

## 3. API / roles / transaction admission

Proposed endpoint vocabulary (final DTOs, enums and status codes frozen with implementing code in SERVORA_MED_API_DRAFT.md):
- GET /api/warehouse/readiness, /locations, /balances, /movements; authenticated ADMIN/MANAGER organization-wide, STAFF read only own vehicle and explicitly granted/needed depot visibility (initial default own vehicle only; never global history/audit). STAFF cannot mutate; demo excluded. Filter/search/page on server; canonical pagination default 6, stable tie-breaker, response metadata consistent snapshot, bounded maximum using existing standard.
- POST /locations, PATCH /locations/:id: ADMIN; ordinary reference updates use expectedVersion, follow ARC-001 for response-caching exemption, no unguarded check-then-act; audit with write. Location owner and type changes constrained by immutable stock history (prefer deactivate/create), stale version 409.
- POST /counts, /receipts, /transfers, /corrections: ADMIN/MANAGER; clientActionId for each critical command; requestHash includes operation, normalized location/product/quantities, actual event date, reason/reference and generation/expected versions where required. Use existing critical-action receipt helper; response minimal IDs/version/status, never entire balance/history or confidential payload. Same key/same payload replay once only if current admission passes; changed payload 409 CLIENT_ACTION_REUSED. Old generation replay of a committed authorized action returns original minimal receipt without new stock; new uncommitted old-generation request conflicts (refresh and use a new ID for deliberate new command). Domain conflict leaves no partial effects. On ambiguous transport outcome retry same ID, on changed business input new ID. Existing timeout/deadlock/serialization conventions, no automatic silent stock mutation.
- GET balance reads include recordedQuantity, verification status, verified generation/count, as-of posting time; UNKNOWN/STALE not presented as usable quantity. No fabricated 'available' quantity before pending handover integration; no reservation. Read combined totals/list from one read-only repeatable-read snapshot. Source reference details restricted by role; don't expose operator identities/customer confidential details to STAFF.

**Critical admission:** current state.ts reader uses pool query, not transaction lock. Operator repository locks operator account -> session -> module-state FOR UPDATE; actual state changes increment version, no-op returns unchanged. Use same transaction client and WAREHOUSE state FOR SHARE for Warehouse commands, held through commit; no actor or operator cross-lock inversion. Check active authenticated BUSINESS user, org/role and session lifecycle under existing auth/user lock order before any receipt claim or replay. Inspect real user/session locking and existing ARC-003 order before implementation; extend explicitly, not duplicate. Warehouse-only commands acquire module-state lock before customer domain locks, then users (sorted, strongest necessary), products (sorted), locations (sorted), readiness/balance keys (sorted); existing critical-action claim order must be reconciled so replay admission occurs before receipt read and no old caller regresses. Current runCriticalAction replays before work callback: checking only inside work is unsafe. Coordinate with #515 ACC-A proposal for smallest opt-in pre-claim admission on same PoolClient (or equivalent verified helper), preserve old behavior and avoid two independent receipt implementations. A response replay must not bypass disabled/role checks. No network call while locked. Bound lock/transaction wait; test both commit orders against operator toggle, offboarding/product delete and concurrent commands. For WH-004 existing JobCard receipt/user/job locks need independent review; do not impose this proposed standalone order blindly onto Core. If lock order conflict found, stop that slice and reconcile contract rather than introducing deadlock or bypass.

Physical count input is an observation, not a command to overwrite history. Require a short-lived server-derived count baseline token/version for the selected stock keys and generation (or equivalent atomic precondition) so a concurrent stock movement or count after observation rejects stale confirmation. Lock all affected keys, verify baseline and generation, then compare retained ledger projection and append delta. Never accept a stale screen's physical quantity over a newer transaction. WH-004 adds pending-handover coverage and physical source capture, not merely a timestamp heuristic.

## 4. Restore, audit and rollout

All module tables included in backup/restore validation even when off. Reconcile ledger/projection FULL OUTER JOIN by org and stock key, transfer pair/header/line completeness, count difference and zero-line evidence, valid readiness source/generation and valid references, no negative quantities. A valid stale generation after restore is not corruption; state and data rewind together; a readiness generation in the future or mismatched evidence fails. Restore must fail with explicit integrity diagnostic, never auto-rebuild or erase data. Operator reset remains MOD-002. Add current migration catalog and health schema/env example updates; no modify of applied 075. Record append-only audit event per business command with actor/organization/UTC instant/action/subject/version/structured before-after evidence, redacted safe data; operator toggle audit remains separate. Test forced audit/receipt failure rolls back mutation.

First implementation PR updates DECISIONS.md (new non-colliding warehouse decision ID referencing MOD-001/002/003), PRODUCT_REQUIREMENTS.md (post-MVP optional extension, not rewrite historical MVP), SERVORA_MED_ARCHITECTURE_PLAN.md (ownership), SERVORA_MED_SCHEMA_DRAFT.md (actual tables/constraints/lock ordering/restore), SERVORA_MED_API_DRAFT.md (actual paths/roles/DTO/error/replay), SERVORA_MED_MVP_SLICES.md (post-MVP slice reference), docs/features/warehouse-* (accepted slice, readiness, rollout/tests), docs/README.md index. ## 5. Cross-module contracts to carry forward

- #516 maintenance direction (07): Maintenance owns assets, service cases and part-use facts; Warehouse owns actual stock movement and quantity. With Warehouse off/unready, service work can complete with structured part-use fact and no automatic stock effect; reconciliation on enable, no historic backfill. When both ready, confirmed part consumption and actual return use explicit source identity and module-owned atomic or durable narrow handoff; no automatic credit on service invalidation. Installed asset serial identity not inferred from stock SKU or delivery quantity. WH-006 / MNT-009 jointly specify source/permissions/replay and four on/off combinations before implementation.
- #515 accounting direction (08): invoice/reference/quote/payment are commercial facts, not evidence of physical receipt/issue; receipt document reference is informational. No finance prerequisite for stock, no warehouse prerequisite for accounting. Purchase document, physical receipt and payment are separately owned; optional durable explicit links, no double posting. ERP authority cutover only when a real integration is approved; one authority per quantity, no M2/M3 in WH-A. WH-008 jointly specifies cutover and external side-effect deduplication.
- Neither sibling PR is modified or treated as merged. No dependency on calendar/messaging/overview. Preserve DOM-001/004/006 and SALE-002 until explicit later supersession.
